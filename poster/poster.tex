    \block{Introduction}{
       We propose a distributed order fulfillment architecture designed for high-throughput e-commerce platforms. Modern online retailers like Amazon need reliability during traffic spikes and consistency for concurrent orders. Our system addresses these with orchestrated parallel verification, priority-based task queuing, and fault-tolerant two-phase commits for payments and shipping.
	}

    \block{System Model}{
The system follows a \textbf{distributed orchestration} model. A client submits an order to the \textbf{orchestrator}, which initiates \textbf{multithreaded parallel calls} to the \textbf{identity} and \textbf{inventory services}. These services perform \textbf{READ requests} against the \textbf{leader database} to validate the request. After receiving \textbf{APPROVED} responses from both services, the orchestrator adds the order to a \textbf{priority queue}. \textbf{Auto-scaling executors} then process orders from the queue, coordinating \textbf{two-phase commit (2PC)} transactions with the \textbf{shipping} and \textbf{payment services} which guarantees \textbf{ACID compliance} for writes. After both services acknowledge (\textbf{ACK}) the \textbf{Commit phase}, the executor \textbf{dequeues} the order and triggers the \textbf{notification service} to inform the user. Throughout this workflow, the \textbf{analytics service} asynchronously logs requests, errors, and metrics for observability. The design prioritizes \textbf{scalability} (with auto-scaling and multithreading), \textbf{consistency} (with 2PC and leader DB reads), and \textbf{fault tolerance} (with queue-based retries and analytics monitoring).

        \block{Commitment Protocol}{
    
The system uses \textbf{two-phase commit (2PC)} between the \textbf{executor}, \textbf{payment}, and \textbf{shipping service} to ensure atomic order processing. To handle failures, the system uses \textbf{optimistic exponential backoff} retries. If retries breach a set threshold, the \textbf{analytics service} can be used to track all logs, errors, and other specific order failure information.

        \block{Replication}{

Two types of replication are used in our distributed system:
\subsection*{Executor Replication (Queue-Based)}  
\textbf{Auto-scaling executors} are stateless and rely on the \textbf{priority queue} for order assignment. Unlike database replication:
\begin{itemize}  
    \item \textbf{Durability}: Orders persist in the queue until successfully processed.
    \item \textbf{Elasticity}: Executors scale dynamically based on queue size.  
\end{itemize}  

\subsection*{Database Replication (Leader-Follower)}  
The database system uses \textbf{synchronous leader-follower replication}. The \textbf{leader} handles all writes and the \textbf{followers} serve read requests. This behavior allows for:  
\begin{itemize}  
    \item \textbf{Strong consistency}: Followers mirror leader state before acknowledging reads.  
    \item \textbf{Fault tolerance}: Automatic elections during leader replica failure minimizes database downtime.  
\end{itemize}
